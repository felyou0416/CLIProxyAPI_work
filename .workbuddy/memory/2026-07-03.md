## 修复 Token 解析 bug: 嵌套 JSON 导致部分请求 token 无法提取

**根因**: `parsing.py` 第 20 行的 `_USAGE_RE = r'"usage"\s*:\s*(\{.*?\})'` 使用非贪婪 `.*?` 匹配 JSON 对象，当上游返回的 `usage` 包含嵌套对象（如 `prompt_tokens_details`、`cost_details`、`completion_tokens_details`）时，`.*?` 会在第一个 `}`（嵌套对象结尾）处停止，截断 JSON 导致 `json.loads()` 失败，token 静默归零。

简单格式 `{"prompt_tokens":500,"completion_tokens":200,"total_tokens":700}` 能正常解析，解释了为什么**有的请求有 token 有的没有**。

**修复**: 
- 新增 `_extract_balanced_json()` 函数，用花括号计数法正确提取嵌套 JSON
- `_extract_usage_tokens()` 改为遍历所有 `"usage"` 出现位置，逐个尝试解析，直到成功
- 移除不再使用的 `_USAGE_RE` 正则

## 累积 Token 统计持久化存储

**背景**: 当前 Dashboard 仅缓存最近 ~300 条事件（15s 滑动窗口），原始日志超过 50 个文件即归档删除（归档上限 2000 条）。一旦事件滑出窗口，token 统计数据永久丢失。但无限保存原始日志会导致存储膨胀。

**方案**: 新增 `backend/request_metrics/cumulative.py` 增量累积存储模块：
- 每次 observability 刷新时自动调用 `update_cumulative_stats(events)`
- 按 **模型 / 客户端 / Provider / 日期** 四个维度聚合 token 用量
- 基于事件 `timestamp` 去重，重复刷新不会重复计数
- 持久化到 `STORAGE_DIR / cumulative_token_stats.json`（日增量 ~2KB，全年 ~700KB）
- 每日数据保留 90 天自动清理，总计/按模型/按客户端/按 Provider 永久保留
- API 端点：`GET /api/cumulative-stats`

**改动文件**:
- `backend/request_metrics/cumulative.py` — 新增，累积统计核心模块
- `backend/request_metrics/observability.py` — `build_observability_snapshot()` 中调用 `update_cumulative_stats()`
- `backend/request_metrics/__init__.py` — 导出新模块
- `backend/routes/get_routes.py` — 新增 `/api/cumulative-stats` 端点

## 再次修复日志/Token 解析 bug

**根因 1**：`_extract_balanced_json()` 之前没有区分 JSON 字符串内部的花括号，若 usage 对象里某个字符串值包含 `{` 或 `}`，会导致深度计数错误，提取失败。

**根因 2**：流式响应（如 Anthropic）的 prompt token 和 completion token 可能分别出现在 `message_start` 和 `message_delta` 两个 usage 对象里，之前只取第一个 usage，会漏掉 completion token。

**修复**:
- `_extract_balanced_json()` 改为识别 JSON 字符串与转义字符，正确跳过字符串内的 `{/}`
- `_extract_usage_tokens()` 改为遍历所有 usage 对象并合并（prompt/completion 取最大值），兼容流式拆分场景
- 缓存版本号升到 `3`，强制重新解析所有日志

## 修复 API Key 掩码格式不匹配导致默认 Key 显示错误

**根因**：代理日志中的 Authorization 掩码格式是 `前4位+...+后4位`（如 `clip...yapi`、`sk-c...mvB4`），而 `backend.api_keys._mask_key()` 使用 `前14位+...+后4位`（如 `sk-cliproxy-wHJ...mvB4`）。`_build_api_key_label_map()` 用 dashboard 掩码做 key，导致日志里的 group_key 匹配不到虚拟 Key 名称，默认 Key 只显示 mask 值。

**修复**:
- `_build_api_key_label_map()` 改用代理一致的 `_proxy_style_mask()`（前4+...+后4）
- `virtual_api_keys.json` 中默认 Key 改为实际代理使用的 `cliproxyapi`（runtime/state.json 中 `last_proxy_api_key`）
- `_resolve_label()` 简化为直接查表

**注意**：旧归档事件（2026-07-02 及之前）是在修复前写入的，缺少 `api_key_masked` 和 token 字段，仍会按 IP 分组并显示为无 token。这些记录会在归档 2000 条上限或 90 天累积清理后自动消失。
